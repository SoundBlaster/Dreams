# macOS CPU/GPU investigation, 2026-11-16

Scope: local Mac mini M2 Pro (12 CPU, 32 GB), macOS 27.2.1 (26B131),
`perf/cpu-gpu-optimization`, base `48027fb5e79efdb96a3b3bf62cd70e88f2663bc3`
(`v0.1.15`). No release, push, installed-app replacement or VM changes.
The source tree was clean at entry. Working-tree hashes identify the candidate;
the base SHA alone does not identify the changed executable.

## Hot path and ownership

| Boundary | Observed implementation and cost |
| --- | --- |
| External idle controller | User LaunchAgent owns a Python process and one full-control `Dreams --mcp`. Polls idle/session state once a second; starts after 300 seconds and stops on input. This controller is outside the repository. |
| Desktop/session | `DesktopInstance` grants a single desktop lease. `DreamsController` creates per-display renderers, owns duration/sleep assertions, and checks capture-tool windows at 10 Hz while rain is active. Stopping closes overlays and cancels that watcher. |
| Cadence | `RainRenderer` is the MTKView delegate. Existing policy: 30 fps with glow or Low Power Mode; otherwise screen refresh capped at 120. Drawable acquisition can block; its wall time is not CPU consumption. |
| Events | One `KeywordFeedReader` per process observes the directory, coalesces notifications over 20 ms and refreshes at a one-second fallback. Renderers consume cached snapshots by revision, independently de-duplicate events, update activity, and create event/keyword selections. |
| Simulation | `MatrixSimulation.advance` maintains deterministic column schedules, cells, head trials, search occupancy and captured fade lifetimes. Version 0.1.15 already transfers cell-array ownership before mutation and skips the default no-op visibility pass. |
| Instances | `MatrixRain.draw` walks enabled columns/rows, computes opacity/head/pulse/colour and emits core/halo instances. The baseline converts each code glyph to a String, prepends `code:`, then hashes/compares Unicode keys even though the atlas was populated in the constructor. Its temporary instance arrays are reallocated every draw. |
| Metal | `encode` copies each nonempty instance array to a new shared MTLBuffer (one core and optionally one halo buffer). Command buffers retain that storage. GPU draws six vertices per instance; core grain and overlapping diffuse halos run in `Rain.metal`. There is no compute simulation on GPU. |
| Preview | Separate renderer/clock, shared feed reader. Offscreen PNG rendering uses the same instance builder/shader and awaits GPU completion. It is distinct from the window compositor and physical scanout. |

The installed-app `sample` contains a substantial `glyph`/String-normalization
branch under `MatrixRain.draw`, plus simulation, opacity and buffer creation.
It also includes waiting for drawables. The process restarted during investigation;
this sample is diagnostic stack evidence, not a stable utilization estimate.

## PID changes

The idle-controller log contains repeated `dreams_status` failures with
`Keyword mailbox is busy; retry the update.` at 13:22:48, 13:23:08, 13:23:23 and
13:24:45 Moscow time. The source explains the chain:

1. `DreamsController.status()` calls synchronous `KeywordFeed.snapshot()`.
2. Snapshot uses a nonblocking exclusive file lock and throws on contention.
3. The Python controller treats any MCP `isError` as fatal, unwinds, closes MCP
   stdin and exits. The log also records MCP EOF.
4. LaunchAgent `KeepAlive=true` restarts the controller and its child.

Thus a new PID need not mean a renderer crash. This also rebuilds the atlas and
resets animation. A bounded retry for this transient error is a separate useful
follow-up; neither the external controller nor status freshness/error semantics
are silently changed by this patch.

## Candidates and implemented scope

1. **Implemented:** index code-glyph UVs by the simulation's repertoire index.
   Preserve atlas population order, glyph fallback, fonts and keyword Unicode
   handling. Searching keyword cells still use code glyphs; settled letters
   still use the lazy word cache.
2. **Implemented:** retain CPU core/halo array capacity on the renderer. Encoding
   still copies into independent Metal storage before subsequent draws, including
   interleaved async previews. Capacity is released with the renderer, and can
   retain the largest previously rendered grid during its lifetime.
3. **Deferred:** reuse Metal buffers via a completion-aware pool. Current allocation
   counters should remain nonzero; this change does not solve the whole instance
   buffer issue. Reusing storage without tracking GPU completion would be unsafe.
4. **Deferred:** capture-tool polling and status-lock retry. They affect lifecycle
   guarantees and require distinct tests; the windowed probe excludes the former.
5. **Deferred:** halo shader/overdraw optimization. Disabling glow or reducing
   cadence/quality would not be an equivalent optimization. No shader, dimensions,
   FPS policy, simulation, event semantics or default setting changed here.

## Build and verification method

Swift 6.4 with installed macOS SDK 26.5, arm64 Release, ad-hoc signing. This host's
CLT SDK 27 lacks `SwiftUIMacros`; the first ordinary build failed. The wrapper now
accepts `DREAMS_MACOS_SDK`, retaining `macosx` as its default. Both A/B executables
use 26.5 through the same build settings. Build outputs remain in this checkout
and its `artifacts` directory; the Egor-host-only TB5 rule does not apply to this
`aotd` Mac mini. The ordinary `make app` entry point is
retained. Rebuilt `DreamsMatrix.ttf` matches the tracked font byte-for-byte.

```
DREAMS_MACOS_SDK=macosx26.5 make app
DREAMS_MACOS_SDK=macosx26.5 zsh scripts/swift-macos.sh test -c release \
  -Xswiftc -plugin-path \
  -Xswiftc /Library/Developer/CommandLineTools/usr/lib/swift/host/plugins/testing
```

The explicit TestingMacros path repairs CLT test discovery; it is not an
application change. Tests use an isolated `DREAMS_FEED_DIRECTORY`. The new replay
test requires explicit output/baseline directories and never accepts new goldens
automatically. It covers both fonts/backgrounds, glow off/on, saturated search,
Latin/Cyrillic keywords, a tool-call event, grid reconstruction and time rewind.

## Measurement protocol and limits

Five alternating A/B blocks, order AB/BA/AB/BA/AB. Each process uses the existing
full calibration collector, 30 s warmup and 60 s collection, deterministic seed
`0xD2EA5EED`, empty fresh feed, forced steady activity, and the same versioned
`dense-no-glow` scenario: 1920×1080, 160 columns, density 1, search 0.1, restored
font. This is a **windowed production renderer**, not the user's live hook stream
or a fullscreen/multiple-display measurement.

CPU utilization is `(user + system CPU seconds) / measured wall seconds * 100`,
in percent of **one core**; it includes the common collector. Selected frame
stage timings are elapsed wall time. GPU timing is completed command-buffer
duration, not whole-device utilization or energy. Presentation timestamps establish
cadence, not physical scanout. Keep per-run distributions; do not pool percentiles.

The driver temporarily unloads only the Dreams idle LaunchAgent, verifies that
its child exited, then restores the LaunchAgent in `finally`. Every probe uses
its own empty feed and runs before production settings migration/delegate setup.
The driver also records process CPU and IOAccelerator statistics every five
seconds to expose unrelated host load. No sudo/powermetrics is used.

The host was not quiet: independent `triald`, `duetexpertd`, `searchpartyd`, VM
and application spikes appear in the raw snapshots. They were not stopped. All
runs must therefore be read as a repeated local comparison with background load,
not a power-lab result or proof of a particular saving in the installed overlay.
Per-process elapsed CPU counters and stable instance-stage savings are stronger
evidence here than whole-device utilization snapshots.

## Results

All ten reports are valid according to the probe's bounded-run checks: nominal
thermal state `[0]`, zero occluded frames, zero failed/missing GPU callbacks and
no sample overflow. Display: 60 Hz, 2560×1440 logical frame, backing scale 1;
rendered workload remains 1920×1080. This is not a claim that background load was zero.

| --- | ---: | ---: | ---: | ---: |
| 1 (AB) | 32.67 | 27.87 | 4.483 | 3.414 |
| 2 (BA) | 33.02 | 29.11 | 4.536 | 3.521 |
| 3 (AB) | 32.72 | 28.85 | 4.419 | 3.507 |
| 4 (BA) | 33.41 | 29.07 | 4.613 | 3.581 |

Medians of the **five run-level values**, not pooled frames:

| Metric | Before | After | Interpretation |
| --- | ---: | ---: | --- |
| Process CPU, % of one core | 32.72 | 29.07 | **−11.2% relative**, −3.65 percentage points of one core |
| Process CPU per draw | 5.457 ms | 4.847 ms | −11.2%; includes the same full collector |
| Instance preparation p50 | 4.509 ms | 3.521 ms | **−21.9%** elapsed stage time |
| Completed GPU command-buffer p50 | 0.7844 ms | 0.7845 ms | No demonstrated GPU improvement |
| Presented interval p99 | 16.6809 ms | 16.6809 ms | Same 60 Hz cadence |

CPU ranges: before 32.06–33.41%, after 27.87–29.47%; every paired CPU and instance
comparison improved. The individual paired CPU reductions span 8.1–14.7%, so
use the median rather than the best run. On a 12-core machine this controlled
scenario's median difference is only about **0.30 percentage points of aggregate
CPU capacity**; it is not an 11-point drop in whole-host CPU load.

Each collection presented 3,600 frames except the first baseline (3,599).
There was one interval over 50 ms in that first baseline, none in the remaining
nine runs; none over 100 ms. Mean core instances stay between 14,399.97 and
14,399.98; tiny count differences follow real-time frame sampling. No halo
instances or glyph rasterizations occur in this no-glow collection. One Metal
instance buffer is still created per submitted frame. GPU work is intentionally
unchanged. IOAccelerator whole-device snapshots include other applications and
show spikes; they do not establish per-process GPU or energy savings.

The result supports this small CPU optimization on the tested macOS workload.
It does not measure its isolated benefit at the user's default density/speed,
in fullscreen/multiple displays, under real hook bursts, with glow enabled,
on a different SDK, or on tvOS. Glow/background/text behavior is covered by
separate pixel tests, not a glow performance claim. Contribution of UV lookup
versus retained CPU capacity was not separately ablated; attribution is to the
combined patch. Allocator events, peak RSS and power remain unmeasured.
