## What changed

Desktop MatrixRain uses an instanced four-vertex triangle strip instead of a
six-vertex triangle list. The shared vertex calculation is factored into
`matrixCorner`; `matrixStripVertex` supplies the four corners. Existing
`matrixVertex` retains all six corners for FPS and tvOS. Fragment code, rects,
UVs, colors, seed, blending, simulation, feed behavior, buffers and frame-rate
policy are unchanged. At 14,400 core instances this removes 28,800 vertex
invocations per frame. It does not eliminate the per-frame Metal buffer copy.

Two further candidates were investigated rather than assumed beneficial:

- Specialized core/glow and transparent/opaque fragment functions produced
  three differing pixels across two of 32 replay PNGs, with maximum channel
  delta 2/255. This experiment is excluded from the retained code. Its source,
  build, PNGs and failure log remain under `specialized*`; no performance claim
  is made for it.
- Persistent Metal pipeline archives and precompiled shader IR were measured
  in separate startup probes. They are not added to production; see below.

## Measurement method and limits

M2 Pro Mac mini, macOS 27.2.1 (26B131), 12 CPUs; one 1920×1080 window on a
2560×1440, 60 Hz display at backing scale 1. Fixed dense fixture: 160 columns,
density 1, restored font, search fraction 0.1, isolated empty mailbox and forced
steady activity. Each new run warms for 10 s and measures for 30 s, with three
alternating AB/BA/AB pairs. Glow=0 and Glow=1 are separate comparisons. These
shorter runs do not supersede the earlier five-pair CPU experiment.

The production idle LaunchAgent is stopped only during a bounded series and
restored in `finally`. No experimental full-control copies overlap. Caffeinate
assertions are scoped to the comparisons. Five-second process and IOAccelerator
snapshots retain unrelated host activity. No builds or other experiments run
concurrently with timing. The host is not otherwise idle or exclusively reserved.

CPU is process user+system delta / measured wall time, expressed as a percentage
of **one core**. GPU values are completed command-buffer timestamps, summarized
per run and then across run-level medians; they are not total-device utilization,
per-process counter shares, power or energy. Compositor work is outside that GPU
timestamp. Validity and cadence are retained separately; no pixel or windowed
result establishes fullscreen, multi-display, physical-screen or TV acceptance.

An initial CLT probe and an initial SDK-comparison probe lacked presentation
callbacks. They are preserved under `rejected-strip-01` and `rejected-sdk-01`,
excluded from numerical comparison, not silently discarded or relabeled valid.

## Startup cache experiment

A standalone Release Swift probe uses the real retained Rain shader, creates
four pipeline variants (opaque/transparent × core/glow), and compares source
compilation, precompiled Metal IR (`Rain.metallib`), and serialized
`MTLBinaryArchive`. Archive loads require `failOnBinaryArchiveMiss`, so a silent
cache miss cannot masquerade as a hit. Each variant gets 20 fresh processes in
alternating forward/reverse order. The system cache is not purged; these are
**warm repeated-launch measurements**, not controlled cold-cache timings.

| Median, ms | Source | Source + archive | Precompiled IR | IR + archive |
| --- | ---: | ---: | ---: | ---: |
| Library creation/load | 0.767 | 0.815 | 0.235 | 0.227 |
| Four pipelines | 1.062 | 0.645 | 1.230 | 0.708 |
| Archive load | 0 | 0.304 | 0 | 0.255 |
| Device creation | 52.654 | 53.500 | 52.493 | 53.074 |
| Total probe | 54.835 | 55.154 | 54.485 | 54.393 |

The first observed source/archive-creation invocation spent 101.77 ms in library
creation and 27.85 ms serializing the archive. This single first observation is
not a controlled cold-cache distribution. In the first IR/archive invocation,
library loading took 0.51 ms but four-pipeline creation took 94.43 ms: IR is not
a ready GPU-specific pipeline binary. The pipeline archive is 64 KB; IR is
16 KB. Real app startup also includes AppKit/font/atlas work and ordinarily only
two pipelines per renderer, which this microbenchmark does not model.

Precompiling IR can avoid runtime source compilation, especially on a cache miss.
The repeated-launch benefit here is about half a millisecond in library loading;
a custom pipeline archive has no demonstrated total startup benefit. An archive
would require device/OS/shader/pipeline identity, invalidation, atomic writes,
corruption recovery and fallback. That complexity is not justified by these
measurements for this small shader. Neither form reduces per-frame GPU work.
The isolated probe, cache files, 80 raw observations and build commands remain in
`artifacts/sdk-20261116/cache-probe/` for a later startup-focused investigation.

Apple documents [Metal libraries](https://developer.apple.com/documentation/metal/metal-libraries)
and [persistent binary archives](https://developer.apple.com/documentation/metal/creating-binary-archives-from-device-built-pipeline-state-objects).
No private cache flags or system-cache deletion were used.

## Validation and results

Final run-level comparisons and validation outcomes follow below. [Specification impact](../../specs/performance/validation/2026-11-16-sdk-gpu/README.md)

### GPU results with Xcode 27.2 / SDK 27.2

Every retained run was valid, with nominal thermal state 0 and no missing
presentation callbacks. Table values are medians of three run-level values.

| Profile / metric | Six vertices | Four vertices | Relative change |
| --- | ---: | ---: | ---: |
| Glow 0: GPU p50, ms | 0.7820 | 0.6249 | −20.1% |
| Glow 0: GPU p95, ms | 1.0129 | 0.8740 | −13.7% |
| Glow 0: CPU, % one core | 26.76 | 27.03 | +1.0%, within observed variation |
| Glow 0: presented interval p99, ms | 16.6808 | 16.6808 | unchanged |
| Glow 1: GPU p50, ms | 4.3313 | 3.8908 | −10.2% |
| Glow 1: GPU p95, ms | 5.1256 | 4.6994 | −8.3% |
| Glow 1: CPU, % one core | 19.46 | 18.80 | −3.4%, not a robust CPU attribution |
| Glow 1: presented interval p99, ms | 50.0418 | 50.0418 | unchanged |

GPU p50 improves in every pair. No-glow runs contain 1,801–1,802 draws and no
intervals over 50 ms; glow runs contain 900–901 draws. Glow's long-interval
counts (before/after) are 40/45, 77/78 and 91/94; none exceed 100 ms. Nominal
cadence is still 30 fps with glow, but these results **do not demonstrate improved
pacing**. Mean core instances stay about 14,399.97–14,399.99; glow adds the same
number of halo instances. Workload geometry, halo brightness and frame policy
are preserved. The larger glow cost is consistent with expanded, overlapping
halo rectangles and procedural cloud fragments; this is not a per-pass counter
attribution. GPU frequency/energy were not measured.

The independent earlier CLT/SDK 26.5 screening also gave 0.7832 → 0.6236 ms
(−20.4%) over three valid alternating no-glow pairs. That establishes replication
on both build toolchains, not a new SDK benefit or a sum of percentage savings.

### SDK/compiler comparison (same CPU checkpoint code)

| Pair | SDK 26.5 CPU, % one core | SDK 27.2 CPU, % one core | Old GPU p50, ms | New GPU p50, ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 24.02 | 26.83 | 0.7870 | 0.7823 |
| 2 | 27.10 | 27.05 | 0.7811 | 0.7800 |
| 3 | 27.04 | 26.27 | 0.7840 | 0.7812 |

Run-level medians: CPU **27.04 → 26.83% of one core**; GPU p50 **0.7840 →
0.7812 ms**. Paired CPU changes are inconsistent and the old run range
24.02–27.10% overlaps the new 26.27–27.05%. This does **not establish an SDK
performance benefit or regression**. All six retained runs are valid with
thermal state 0, no missing presentations and no intervals over 50 ms.
The practical demonstrated SDK benefit is a working current build/test toolchain,
not reduced runtime CPU/GPU.
