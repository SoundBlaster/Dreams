## Scenarios

| Scenario | Contract composition | Evidence limit / decision |
| --- | --- | --- |
| Opaque start on selected monitors, Esc on the key overlay | displays selects eligible targets; presentation owns one window per target; exit callback invokes session.stop for all | Existing OverlayExitTests declares this; no live WindowServer run in this pass |
| Click empty rain, then Exit button | Ordinary click changes key/responder and reveals controls; button invokes session stop | UI click delivery/accessible button reachability need a fresh native run |
| Work on an uncovered monitor, press Esc there | Reconcile does not ordinarily retake focus; another application receives its own Esc | Parent relies on actual key-window ownership; no global Esc guarantee |
| Overlay appears with a stationary cursor already over Exit | Initial reveal does not sample the cursor; pointerOverButton remains false until mouseMoved (or is cleared by mouseExited) | O7: the timer can hide the button under that cursor when the other hide guards permit it; source observation only |
| Transparent overlay and working application | Nonactivating/key-disabled panels ignore mouse; no per-overlay exit controls; global hotkey/explicit stop remain | Transparency alone does not prove tool-specific pixel capture or keyboard behavior |
| Closed laptop lid / external main monitor | Inventory without built-in screen selects main eligible external; stored subset persists through reconnect | No physical clamshell/topology test was run |
| Remove one selected monitor or every eligible monitor | Manager prepares additions then removes obsolete windows; controller preserves requested session, timer and saved choices | Empty ownership is not stopped state; focus restoration after complete disconnect is not universally promised |
| Renderer initialization fails during reconcile | Newly prepared additions close; working windows remain; selection caller rolls back its policy on failure | Initial begin already stopped its predecessor, so failure there stops the new session instead; no universal transaction guarantee |
| Interactive opaque / transparent vs finite agent start | Four duration/input profiles share session/presentation contracts | Timer and OS scheduling can delay completion; no hard real-time exit latency |
| Screenshot picker appears/disappears | CaptureVisibility orders owned windows out/front without changing requested session or expiry | O1 corrected: rain_visible false / rain_suspended_for_capture true while suspended; deterministic observation/clock regression covers both backgrounds, not real picker recognition or pixel evidence |
| Shortcut conflict or failed rollback | New registration can fail; previous registration is attempted again | O2: rollback result is not checked and status can be stale; no guaranteed global backdoor under all OS failures |
| Shortcut recording receives Esc | Temporary local monitor cancels recording and consumes event | Intentional recording context exception to local opaque Esc routing |
| Resume after agent prepare_ui | Prepare UI stops session; resume uses remembered full duration/brightness | Does not restore old expiry deadline; workspace remains separately owned |

## Review backlog

- **O1 — capture-status mismatch corrected (controller/MCP consumer).** `rain_visible` now requires a requested session, owned windows and no capture suspension. Additive `rain_suspended_for_capture` distinguishes temporary hiding from stop or absent targets. Regression covers both backgrounds, the restore grace period, repeated picker activity and stop while suspended. Actual pixel visibility remains outside this status guarantee.
- **O2 — shortcut rollback/status (exit adapter).** `change(to:)` ignores the result of re-registering the previous hotkey. The delegate does not clear its registration Boolean on that failure path. Decide whether to report an unavailable global shortcut and reconcile status; this pass does not modify behavior.
- **O3 — focus after topology/capture transitions (presentation owner).** Focus return is conditional and macOS activation can fail. `hasPresented` can remain set while no targets exist; a reconnect need not reacquire opaque focus automatically. Decide on desired recovery behavior and verify with actual monitors.
- **O4 — capture/privacy boundary (platform consumer).** `sharingType` and process-name detection are best-effort. No guarantee is made for all recorders, tools or macOS versions, nor for screen locking/secrecy. Opaque windows still take input while merely hidden from capture; use explicit prepare_ui stop.
- **O5 — profile-change failure (session owner).** Transparency preference changes before the active-session restart; a restart error does not roll the preference back. Recovery behavior should be reviewed separately from explicit display-selection rollback.
- **O6 — broader interfaces (future recovery).** Full MCP protocol/EOF/publisher authority, hook mailbox/privacy, renderer algorithms and private virtual workspace lifecycle remain unexplored contracts. Only their overlay entry/callback wiring is in scope here.

- **O7 — uninitialized pointer tracking (exit control).** `pointerOverButton` begins false and is updated only by mouseMoved or cleared by mouseExited. Window attachment and mouseEntered reveal the button without sampling cursor position, so a stationary cursor over Exit does not guarantee persistent visibility. The draft describes the tracked flag; sampling the cursor at presentation remains a separate runtime fix.

## Evidence and acceptance

The supplied sources establish scoped implementation observations and conditional integration reasoning. Source declarations in DisplaySelectionTests, OverlayExitTests and test-overlay-exit.py show intended scenarios, not executed results. Structural HC/SpecPM validation establishes schema/cascade support only. The capture-status correction adds scoped native-overlay runtime evidence with injected observations/time. Physical Escape/hotkey input, accessibility, real screenshot-picker detection and display topology still need separately identified runtime evidence. All requirements remain descriptive drafts; merging documentation does not accept them as product guarantees.
